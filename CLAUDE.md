# deckwright

Сервис: читает произвольный `.pptx` как набор правил и собирает по нему новые
слайды. Кейс VK Tech «Цифровой дизайнер презентаций», ЛЦТ 2026.

## Стек

Python 3.11 · python-pptx + lxml (OOXML) · fontTools (метрики текста) ·
Pydantic (контракты слоёв) · LibreOffice headless (pptx→pdf) · poppler (pdf→png) ·
Streamlit (UI) · OpenAI-совместимый клиент к модели с открытыми весами.

## Команды

```bash
pip install -e ".[dev]"                                  # установка
ruff check .                                             # линтер   (gate)
pytest -q                                                # тесты    (gate)
python -m deckwright.cli run --config configs/config.yaml --template T \
  --brief "бриф" --input отчёт.docx --purpose project    # вход в любом виде
streamlit run app/ui.py                                  # веб-интерфейс
docker compose up --build                                # всё в контейнере
```

Гейты `ruff check .` и `pytest -q` обязаны быть зелёными в конце каждой фазы.

## Архитектура в десять строк

```
бриф + файлы ─►[0 content]─► ContentPack  факты, ряды, цитаты; числа сверены с входом
template.pptx ─►[1 parse ]─► TemplateSpec  токены, layouts, паттерны, шрифты, декор
ContentPack  ─►[2 plan  ]─► DeckPlan      слайды: намерение, заголовок-вывод, блоки, данные
Spec+Plan+strategy ─►[3 layout]─► SlideIR  абсолютные боксы, стили из токенов, provenance
SlideIR ─►[4 render]─► .pptx ─► .pdf ─► .png ; .html
SlideIR+.pptx+.png ─►[5 audit]─► Issue[] ─► UI ─► выбранные ─►[fix]─► 3→4→5
```

Каждый слой — пакет с одним входом, одним выходом и Pydantic-контрактом в
`schemas/`. Слои не лезут во внутренности друг друга. `SlideIR` — единый
источник истины для всех форматов экспорта и для детерминированного аудита.

Ключевое решение: шаблон используется **как донор**. Композиция не рисуется
заново, а клонируется поддеревом фигур из слайда-примера с заменой текста.
Обоснование — `research/research.md` §5.

С донора переносится и его собственный фон (`p:bg`). Фото донора — место под
картинку (`Pattern.photo_slots`, признаки изображения, не имя фигуры), а не
содержание: в колоду не переносится; логотипы, значки и декор остаются.

Шаблон без плейсхолдеров (бланк из обычных фигур) разбирается по фигурам:
роли — по геометрии, кеглю, положению и повторам; имена фигур — только
подсказка. Проверяется на двух бланках: `data/holdout/dorozhnaya_karta.pptx`
и синтетическом без имён (`tests/fixtures/make_blank_template.py`). Номера
1…n в фигурах одного размера — порядковые места, подпись, повторённая внизу
нескольких слайдов, — колонтитул, копии фигур стопкой — один элемент.
Шаблон с фото — `data/holdout/podgotovka_k_ekzamenam.pptx`; записанные живые
планы «продажи» — `tests/fixtures/{roadmap,exam,vk_tech}_sales/`.

Подбор композиции: единственный показатель слайда — не мельче типичного
заголовка шаблона; график и таблица — на основном фоне шаблона, не на
акцентном (фон меньшинства композиций); ряд карточек продолжают места той же
роли под ним («две + широкая»); после двух повторов композицию сменяет та,
где текст влезает кеглем своего места. Переполненный заголовок занимает и
строки под рамкой. Ячейки таблицы — цветом таблиц шаблона, числа ячеек — той
же записью, что числа графиков. Записанные планы пробы 4×4 —
`tests/fixtures/{vk_tech_pdf,zelenie_pdf}/`.

Шаг с моделью — агент `agents/<имя>.vN.yaml` (модель, промпт, параметры,
пределы); параметры шагов только там, `config.yaml` перечисляет агентов,
версии и хэши агентов — в `RunManifest.agents`. Промпт шаг берёт из агента
(`config.agent_prompt`). План короче `deck.min_slides` — невалидный ответ.
Наборы для сдачи — `outputs/demo/{observability,sales}/`
(`scripts/demo_set.py`: колоды по живому плану, время и находки из лога).

Числа на графиках пишутся форматом по самим данным и с локалью языка колоды
(`charts.number_format`: «41 380», «14,2», «1,2 млн») — ни `General`, ни `0`.
Аудит по картинкам получает слайд при `audit.contextual_dpi` (96: при 72 и 60
на живой модели теряется находка, run 32). Время прогона — по пяти этапам
(`pipeline.stage_times`) в CLI, `run-summary.json` и интерфейсе.

Три варианта раскладываются по очереди (композиции не повторяются между
ними), собираются, проверяются и исправляются параллельно. Текстовый проход
аудита — один на колоду. Провайдер модели на тарифе L0 даёт 40 000 токенов
в минуту — ограничитель `llm/ratelimit.py` ждёт, а не падает.

## Правила

1. Никакого хардкода под конкретный шаблон: ни имён, ни координат, ни цветов,
   ни имён layout'ов, ни числа слайдов. Всё извлекается из файла шаблона.
2. Промпты и имена моделей — только в `prompts/` и `agents/`, версионируемыми
   файлами. В `.py` их нет.
3. Растеризация слайда в картинку для `.pptx` запрещена.
4. Никакого рефакторинга «заодно», улучшений без привязки к критерию приёмки и
   абстракций «на будущее».
5. Мусорные файлы в репозитории запрещены: отладочные скрипты, `test2.py`,
   сгенерированные артефакты вне `outputs/`.
6. Секреты только в `.env` (+ `.env.example`). В `config.yaml` — ссылки `${VAR}`.
7. Ответ LLM — структурированный JSON по Pydantic-схеме с валидацией и
   ограниченным числом повторов. Регулярки по свободному тексту запрещены.
8. «Готово» не заявляется без зелёных гейтов и прохода по критериям приёмки.
9. Фаза, добавляющая вызовы модели, завершается замером времени по этапам —
   в `progress/handoff.md`. Бюджет пять минут на колоду — **вместе с разбором
   входа** — проверяется цифрами после каждого такого шага, а не один раз в
   конце.
10. Цифры на слайдах — только из входа. Число, которого во входе нет,
   отбрасывается при разборе (`content/grounding.py`) и ловится аудитом
   (`content.undeclared_number`).
11. Живая модель доступна только из GitHub Actions (`llm-probe.yml`, секрет
   `LLM_API_KEY`); из среды разработки — нет. Результат живого прогона
   забирается из лога (`get_job_logs`), артефакты недоступны.

## Документы

| что | где |
|---|---|
| исследование, разбор старого репозитория и датасета | `research/research.md` |
| контракт: scope, ограничения, критерии приёмки A1–A25 | `specs/spec.md` |
| фазы, тесты, Challenge Log | `plans/plan.md` |
| журнал прогресса по фазам | `progress/handoff.md` |
| листы до/после приёмки сентября, сравнение dpi | `outputs/review/sales-sept/` |
| листы до/после шести дефектов вёрстки | `outputs/review/layout-defects/` |
| наборы для сдачи: таблица, сводный лист, pptx/pdf/html | `outputs/demo/{observability,sales}/` |
| пайплайн и границы слоёв | `docs/ARCHITECTURE.md` |
| модели, лицензии, требования | `docs/MODELS.md` |
| проверки аудита и покрытие | `docs/AUDIT.md` |
