# Спецификация: «Цифровой дизайнер презентаций»

Версия 1.0 · статус: на согласовании · источник требований — ТЗ VK Tech
(Приложение А задачи) и раздел 5 постановки.

Этот документ — **контракт**. Готовность работы проверяется по разделу
«Критерии приёмки», а не по ощущению.

---

## 1. Проблема

Презентация в фирменном стиле сегодня делается в два прохода разными людьми:
автор пишет содержание, дизайнер раскладывает его по шаблону — подбирает макет,
двигает блоки, ищет иконку, перекрашивает диаграмму в корпоративный цвет.
Языковые модели закрывают первый проход и не закрывают второй: они пишут текст,
но не воспроизводят дизайн-систему.

Разрыв именно здесь: **нет инструмента, который прочитает произвольный чужой
шаблон как набор правил и соберёт по нему новые слайды**.

## 2. Цель

Сервис, который принимает произвольный `.pptx`-шаблон и краткий бриф с
контент-пакетом, а отдаёт готовую презентацию на 10–15 слайдов, собранную по
правилам этого шаблона, в трёх визуально различимых вариантах вёрстки, с
нативными объектами в `.pptx`, встроенным аудитом качества и экспортом в
`.pdf` и `.html`.

## 3. Scope

1. **Импорт и декомпозиция шаблона.** Произвольный `.pptx` → `TemplateSpec`:
   палитра, гарнитуры, типографическая шкала, поля и сетка, layout'ы с ролями
   плейсхолдеров, библиотека композиционных паттернов, повторяющиеся элементы
   (логотип, колонтитул, номер слайда), встроенные шрифты.
2. **Импорт контент-пакета** (`.pdf`/`.docx`/`.pptx`/`.txt`/`.md`) → нормализованный
   набор фактов, числовых рядов и цитат с привязкой к источнику.
3. **Планирование.** Бриф + назначение (фича / продукт / проект / инициатива) +
   контент-пакет → `DeckPlan`: состав слайдов, их порядок, намерение каждого,
   заголовок-вывод, содержательные блоки, данные — **до** вёрстки.
4. **Вёрстка.** `TemplateSpec` + `DeckPlan` + стратегия → `SlideIR`: абсолютные
   боксы, стили только из токенов шаблона, детерминированное разрешение
   переполнения текста.
5. **Визуализация.** Графики, таблицы, диаграммы, пиктограммы и SmartArt-подобные
   схемы — нативными объектами в палитре шаблона.
6. **Три варианта вёрстки** на одном контенте и одном шаблоне, различающиеся по
   одной явно заданной оси, одинаково соответствующие правилам шаблона.
7. **Экспорт**: `.pptx` (нативные объекты), `.pdf`, `.html`, PNG-превью.
8. **Аудит как часть пайплайна**: детерминированные проверки по `SlideIR` и XML
   пакета, контекстные — VLM по PNG слайда. Находки визуализируются в UI,
   пользователь выбирает, что чинить, исправление применяется.
9. **Версионирование скиллов и агентов**: каждый промпт и конфиг агента — отдельный
   версионированный файл; версии пишутся в манифест прогона.
10. **Веб-интерфейс** для десктопа.
11. **Воспроизводимый запуск** одним конфиг-файлом, в Docker.

## 4. Non-goals

- Мобильные и планшетные устройства (ТЗ п.3 прямо снимает это требование).
- Редактирование слайдов «как в PowerPoint» — UI показывает, подсвечивает и
  чинит по выбору, но не является редактором.
- Мультитенантность, учётные записи, биллинг, база пользователей.
- Импорт шаблонов в форматах, отличных от `.pptx`/`.potx` (`.pdf`, Keynote,
  Google Slides напрямую) — вне первой версии.
- Генерация изображений text-to-image: в scope только **интерфейс-слот**
  провайдера; реализация — задача со звёздочкой для топ-10, после основного
  пайплайна.
- Анимации, переходы, видео и звук на слайдах.
- Совместное редактирование, история версий колод.

## 5. Ограничения

| | ограничение | источник |
|---|---|---|
| O1 | Никакого поведения, зависящего от конкретного шаблона: ни `if template_name == …`, ни захардкоженных координат, цветов, имён layout'ов, числа слайдов | ТЗ п.2 «Рамки решения», раздел 7 постановки |
| O2 | В `.pptx` слайд обязан состоять из нативных объектов. Слайд, выгруженный единым растровым изображением, не засчитывается | ТЗ п.2.7 |
| O3 | Генеративные модели — только с открытыми весами, лицензия Apache 2.0 или MIT, LLM/VLM ≤ 35B, text-to-image ≤ 20B. Llama и Gemma не подходят по лицензии | ТЗ п.3 |
| O4 | Генерация одной колоды — не более 5 минут, с замером в логах | ТЗ п.2 |
| O5 | Промпты и конфиги агентов лежат отдельными файлами, не зашиты в код | ТЗ п.4 |
| O6 | Веб-интерфейс работает в актуальной и предыдущей версиях Chrome, Firefox, Safari, Яндекс Браузера на macOS и Windows | ТЗ п.3 |
| O7 | Секреты — только в `.env`, в репозитории `.env.example` | раздел 7 постановки |
| O8 | Переполнение текста решается детерминированно: измерение по метрикам шрифта, уменьшение кегля только по шкале шаблона, далее сокращение текста моделью или разбиение слайда. На autofit PowerPoint не полагаться | раздел 3 постановки |
| O9 | Ответ LLM — структурированный JSON по Pydantic-схеме с валидацией и ограниченным числом повторов. Парсинг свободного текста регулярками запрещён | раздел 3 постановки |
| O10 | Сгенерированные артефакты — только в `outputs/`, `outputs/` в `.gitignore` кроме финальных демо | раздел 7 постановки |

### Ограничения среды (замерены, см. `research/research.md` §3)

| | факт | следствие |
|---|---|---|
| E1 | В базовом образе нет `libreoffice-impress` и `poppler-utils` | ставятся явно в Dockerfile, иначе `.pptx` не открывается вовсе |
| E2 | Встроенные шрифты — EOT с MTX-сжатием, простым срезом не распаковываются | нужен `libeot`/`eot2ttf` + каталог открытых шрифтов как fallback |
| E3 | Шрифта `Play` нет в системе; LibreOffice подставляет свой | без шрифтового тракта PDF, PNG и измерение текста расходятся с реальностью; подстановки журналируются |
| E4 | Исходящая сеть закрыта allowlist'ом | holdout-шаблоны синтезируются локально; внешние стоковые API не используются |
| E5 | `theme1.xml` не отражает реальную дизайн-систему (у `vk_workspace` там стоковая офисная палитра) | токены добываются статистикой употребления, тема — слабый приор |
| E6 | У большинства layout'ов датасета нет контентных плейсхолдеров | паттерны из слайдов-примеров — основной путь подбора композиции, не запасной |

## 6. Критерии приёмки

Каждый критерий проверяется «да/нет» со ссылкой на код или артефакт.

### Парсинг шаблона
- **A1.** Произвольный `.pptx` → `TemplateSpec` без ручных правок. Проверено на
  3 шаблонах датасета и на holdout-шаблонах.
- **A2.** Из шаблона извлечены и лежат в `TemplateSpec`: палитра, гарнитуры,
  типографическая шкала, поля и сетка, layout'ы с ролями плейсхолдеров, позиции
  логотипа и колонтитула.
- **A3.** Шаблон без пригодных layout'ов (колода с оформленными слайдами)
  разбирается успешно: паттерны извлекаются из самих слайдов.
- **A4.** Семантика layout'ов и паттернов («титул», «раздел», «2 колонки»,
  «график+текст») определяется правилами по структуре; VLM по рендеру
  привлекается только там, где правил не хватило, и это видно в `TemplateSpec`
  (поле источника решения и уверенности).
- **A5.** Встроенные шрифты извлекаются и регистрируются; при невозможности —
  зафиксированный fallback, отражённый в манифесте прогона и в аудите.

### Планирование и вёрстка
- **A6.** По брифу и назначению (фича / продукт / проект / инициатива) строится
  `DeckPlan` на 10–15 слайдов или на заданное пользователем число — **до** вёрстки.
- **A7.** Слайды собираются на layout'ах и паттернах шаблона; ни одна координата,
  цвет, гарнитура или кегль не заданы в коде константой.
- **A8.** Переполнение текста разрешается детерминированно по O8; ни один
  сгенерированный слайд не полагается на autofit.

### Визуализация и экспорт
- **A9.** Графики, таблицы, диаграммы, пиктограммы и SmartArt-подобные схемы —
  нативные объекты в цветах палитры шаблона.
- **A10.** Экспорт `.pptx` открывается в PowerPoint и в LibreOffice; на каждом
  слайде есть нативные объекты, ни один слайд не является одной картинкой.
- **A11.** Экспорт `.pdf` и `.html` создаётся из того же `SlideIR`.
- **A12.** Три варианта вёрстки на одном контенте визуально различимы, одинаково
  соответствуют правилам шаблона, ось различий обоснована в `ARCHITECTURE.md`,
  и это **один пайплайн с параметром стратегии**, а не три ветки кода.

### Аудит
- **A13.** Все проверки Приложения 1 ТЗ реализованы либо отказ от каждой
  обоснован в `AUDIT.md`.
- **A14.** Каждая проверка помечена как детерминированная или контекстная.
- **A15.** Каждая находка несёт: id проверки, тип, серьёзность, номер слайда,
  bbox, описание, предлагаемое исправление.
- **A16.** Находки визуализируются поверх слайда в UI; пользователь выбирает,
  что исправить; исправление применяется и колода пересобирается.
- **A17.** Детерминированные проблемы чинятся детерминированно везде, где это
  возможно.

### Инженерия
- **A18.** Вся колода — разбор входа (приведение материалов к контент-пакету,
  разбор шаблона) и генерация трёх вариантов — ≤ 5 минут (300 с). Изначально
  организаторы разрешили не считать разбор входа; с переходом на произвольный
  вход (бриф, файлы, JSON чужой структуры) разбор стал вызовом модели, и
  заказчик включил его в бюджет. Время по этапам пишется в лог и в манифест
  прогона; в `RunSummary` и выводе CLI — разбор входа, генерация и сумма, с
  бюджетом сверяется сумма.
- **A19.** Промпты и конфиги агентов — отдельные версионируемые файлы; в манифест
  каждого прогона пишутся версии промптов, модель, параметры, хэш шаблона, seed.
- **A20.** Используются только модели с открытыми весами, Apache 2.0 / MIT,
  ≤ 35B; всё перечислено в `MODELS.md`.
- **A21.** Веб-интерфейс работает на десктопе в Chrome, Firefox, Safari и
  Яндекс Браузере.
- **A22.** Воспроизводимый запуск одной командой с конфиг-файлом, в Docker.
- **A23.** Документация: `README` (сетап, переменные окружения, ограничения),
  `ARCHITECTURE` (пайплайн, границы слоёв), `MODELS`, `AUDIT` (список проверок и
  покрытие).
- **A24.** Для промежуточной сдачи: 9 презентаций (3 шаблона × 3 варианта)
  сгенерированы и лежат в `outputs/`.
- **A25.** Слои изолированы: каждый — отдельный пакет с одним входом, одним
  выходом и Pydantic-контрактом; слой не обращается во внутренности соседнего.

## 7. Границы контрактов между слоями

| слой | вход | выход | контракт |
|---|---|---|---|
| Parse | `template.pptx` | `TemplateSpec` | `schemas/template_spec.py` |
| Content | файлы контент-пакета | `ContentPack` | `schemas/content_pack.py` |
| Plan | бриф + назначение + `ContentPack` | `DeckPlan` | `schemas/deck_plan.py` |
| Layout | `TemplateSpec` + `DeckPlan` + `LayoutStrategy` | `SlideIR` | `schemas/slide_ir.py` |
| Render | `SlideIR` + `TemplateSpec` | `.pptx`, `.pdf`, `.html`, PNG | — |
| Audit | `SlideIR` + `.pptx` + PNG + `ContentPack` | `Issue[]` | `schemas/issue.py` |
| Fix | `Issue[]` выбранные + `SlideIR` | `SlideIR'` | тот же `slide_ir` |

`SlideIR` — единый источник истины для всех форматов экспорта и для
детерминированного аудита. Каждый элемент `SlideIR` несёт `provenance`: ссылку
на донорскую фигуру шаблона или на токен, из которого взят стиль.

## 8. Что считается «не сделано»

- Критерий из раздела 6 без ссылки на код или артефакт.
- Любая ветка по имени шаблона, layout'а или файла.
- Промпт или имя модели в `.py`.
- Слайд, который в `.pptx` оказался картинкой.
- Красный `ruff check .` или `pytest -q`.
